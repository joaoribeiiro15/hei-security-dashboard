🔒 HTTPS / TLS — Scoring Guide

How the score is calculated

The scanner uses testssl.sh to probe each institution's primary domain. It evaluates protocol support, certificate validity, and the presence of modern security features. The final score (0–100) and grade reflect the overall TLS configuration quality.

Grade thresholds

Grade Score range 💡 What it means
A+ 93–96 + extras TLS 1.2 and 1.3 only, valid certificate, OCSP stapling or DNS CAA configured — the gold standard.
A 93–96 Modern TLS only, valid certificate. Excellent posture with minor optional features absent.
B 88–94 TLS 1.0 or TLS 1.1 still enabled alongside modern versions, or certificate features missing. Functional but outdated protocols remain.
C 70–87 Multiple legacy protocols enabled or significant certificate issues.
D 50–69 Serious weaknesses — SSLv3 or weak cipher suites present.
F 0–49 Critical failures — HTTPS not available, invalid certificate, or SSLv2/SSLv3 only.

💡 Key factors that affect the grade

  • Protocol deprecation: TLS 1.0 and TLS 1.1 are deprecated (RFC 8996). Enabling them lowers the score from A to B range, even if TLS 1.3 is also available.
  • Certificate validity: An expired or self-signed certificate caps the grade at D or below.
  • OCSP stapling: Allows the server to bundle certificate revocation status inline, avoiding extra round-trips to the CA. Its presence contributes to an A+ over A.
  • DNS CAA: A DNS record that restricts which Certificate Authorities may issue certificates for the domain. Absence is not penalised heavily but its presence signals mature security management.
  • Certificate transparency: Inclusion in public CT logs is expected and its absence is penalised.
  • HTTP/2 (ALPN): Indicates a modern server stack; influences A vs A+ distinction at the same numeric score.

FAQ

Why do two institutions with the same score get different grades (A vs A+)?

The grade combines the numeric score with a secondary evaluation of security-enhancing features (OCSP stapling, DNS CAA, HTTP/2, ALPN). An institution scoring 96 with OCSP stapling and HTTP/2 receives A+; one scoring 96 without those extras may receive A. The score measures protocol correctness; the grade rewards additional hardening.

Why does the scanner only see a B even though the site looks secure in the browser?

Browsers are permissive — they accept TLS 1.0 and 1.1 silently. The scanner applies stricter rules aligned with NIST and BSI guidelines. A green padlock in the browser does not imply an optimal TLS configuration.

Does a B grade mean the site is insecure?

Not immediately. A B typically means legacy protocols are still enabled, increasing the theoretical attack surface. The practical risk depends on the client base and whether the server enforces server-side cipher preference.

🛡️ DNSSEC — Scoring Guide

How the score is calculated

The scanner queries each domain using the Google DNS-over-HTTPS API and evaluates whether DNSSEC is deployed. If it is, the score (0–100) reflects the cryptographic strength of the signing algorithms and digest algorithms in use, scored according to RFC 8624 algorithm recommendations.

The RFC 8624 classification assigns each algorithm a score from 0 (MUST NOT use) to 100 (RECOMMENDED). The final DNSSEC score is derived from the algorithm and digest scores of the active key pairs (ZSK and KSK).

Grade thresholds

Grade Score 💡 What it means
A 88–100 DNSSEC deployed with strong algorithms (ECDSAP256SHA256, Ed25519 with SHA-256 digest). RFC 8624 RECOMMENDED.
B 75–87 DNSSEC deployed but using algorithms classified as OPTIONAL or with mixed digest quality (e.g. ED25519 with SHA-384, or RSA with NSEC3 and SHA-256 digest).
C 50–74 DNSSEC deployed but using weak or deprecated algorithms (e.g. RSASHA1-NSEC3-SHA1, RFC 8624 score 25). SHA-1 digest present.
F 0 DNSSEC not deployed. The domain has no RRSIG, DNSKEY, or DS records. DNS responses cannot be authenticated.

💡 Key factors that affect the grade

  • Algorithm choice: ECDSAP256SHA256 (Algorithm 13) is the RFC 8624 RECOMMENDED algorithm and produces scores of 98. RSA-based algorithms (e.g. RSASHA1) are deprecated and pull the score down to the C range.
  • Digest algorithm: SHA-256 (type 2) is recommended. Presence of SHA-1 (type 1) alongside SHA-256 lowers the score because the weakest digest sets the effective security floor.
  • Non-existence proof method: NSEC3 (hashed denial of existence) is preferred over plain NSEC for zones where enumerating all hostnames is undesirable. Both are valid; NSEC3 is standard for most modern deployments.
  • Key types: The Zone Signing Key (ZSK) signs individual DNS records; the Key Signing Key (KSK) signs the DNSKEY RRset. Both must be present and strong for a high score.

FAQ

Why do so many institutions score F?

DNSSEC adoption in Norwegian HEIs is low (37% in this dataset). Deploying DNSSEC requires coordination between the institution's DNS operator and their domain registrar to publish DS records in the parent zone (.no). Many institutions delegate DNS management to third parties who have not enabled DNSSEC.

What is the practical impact of missing DNSSEC?

Without DNSSEC, DNS responses can be forged through cache poisoning attacks (e.g. Kaminsky attack). An attacker could redirect users to a malicious server serving a fraudulent login page for the institution's portal, with no indication to the user that anything is wrong.

Can an institution have DNSSEC but still score B instead of A?

Yes. Deploying DNSSEC with RSA-based algorithms (particularly RSASHA1) produces a B or C because RSA-SHA1 is deprecated by RFC 8624. Migrating to ECDSAP256SHA256 (Algorithm 13) is the recommended upgrade path and typically yields an A score.

Does DNSSEC protect the website content?

No. DNSSEC only authenticates DNS resolution — it confirms that the IP address returned for a domain name is legitimate and has not been tampered with in transit. It does not encrypt the connection or protect the website itself. It is complementary to HTTPS, not a replacement for it.

🔑 Security Headers — Scoring Guide

How the score is calculated

The scanner uses a browser emulator to load each institution's homepage and inspect the HTTP response headers. The final score (0–100) is computed from two components:

  • Header component (60% weight): evaluates the presence and correct configuration of 10 security response headers.
  • Redirect component (40% weight): evaluates whether the site correctly redirects HTTP traffic to HTTPS and stays on the same domain.

final_score = header_component × 0.60 + redirect_component × 0.40

Grade thresholds

Grade Score range 💡 What it means
A 80–100 Most security headers present and correctly configured. HTTPS redirect in place.
B 65–79 Core headers present but several optional or advanced headers missing. Redirect correct.
C 50–64 Only a subset of headers implemented. Some important ones (e.g. CSP, HSTS) missing.
D 40–49 Minimal header coverage. Missing most security headers including HSTS.
E 33–39 Very few headers present. HTTPS redirect may be incomplete or misconfigured.
F 0–32 Almost no security headers. No HTTPS redirect or redirect goes to a different domain.

💡 The 10 evaluated headers

Header Purpose Impact
Strict-Transport-Security Forces browsers to use HTTPS for the domain High
Content-Security-Policy Restricts sources for scripts, styles, images High
X-Frame-Options Prevents clickjacking via iframes Medium
X-Content-Type-Options Prevents MIME-type sniffing Medium
Referrer-Policy Controls referrer information sent to third parties Medium
Cross-Origin-Opener-Policy Isolates the browsing context from cross-origin windows Medium
Cross-Origin-Embedder-Policy Requires cross-origin resources to opt in to embedding Medium
Cross-Origin-Resource-Policy Restricts which origins can load the resource Medium
X-XSS-Protection Legacy XSS filter (deprecated in modern browsers) Low
Access-Control-Allow-Origin CORS policy — controls cross-origin resource access Context-dependent

FAQ

Why is the redirect component worth 40%?

An HTTPS redirect is a prerequisite for most security headers to be meaningful — headers sent over plain HTTP can be stripped by a man-in-the-middle. Institutions that redirect correctly to HTTPS (and stay on the same domain) score 100 on the redirect component. Those that do not redirect, or redirect to a different domain, score lower and cannot fully benefit from headers like HSTS.

Why does an institution with all headers present still score below 100?

Each header is evaluated for correct configuration, not just presence. For example, a Content-Security-Policy set to default-src * (allowing all origins) is present but misconfigured and scores lower than one with a restrictive policy. Similarly, an HSTS header without includeSubDomains and a sufficient max-age is penalised.

Why is X-XSS-Protection listed if it is deprecated?

The header is evaluated because some older browsers still support it and its presence (or deliberate disabling via X-XSS-Protection: 0) remains relevant for compatibility assessments. Modern browsers have built-in XSS protection mechanisms that supersede this header.

Why is Access-Control-Allow-Origin marked as context-dependent?

ACAO is a CORS header — its correct value depends entirely on the institution's intended cross-origin access policy. Setting it to * (open) is appropriate for public APIs but a risk for authenticated portals. The scanner evaluates its presence and checks for obviously permissive configurations.
